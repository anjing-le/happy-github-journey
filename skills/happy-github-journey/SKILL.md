# Happy GitHub Journey

把素材拆成可以关联、复用的知识，帮助用户形成自己的设计判断。

## 定位与当前阶段

先读目标仓库的 `AGENTS.md`、`README.md`，写内容时读 [内容格式](references/content-format.md)。优先使用用户指定的仓库；本 Skill 随仓库保存，仓库副本的根目录是本 Skill 目录的上两级。通过本机符号链接调用时先解析真实路径；复制安装时不能凭该相对路径定位项目。

当前是待真实样例校准的初稿。用户希望先收录链接，再用一条完整素材调整第二、三层的粒度，认可后处理其余待办。尚未校准时先形成一条供用户检查的初稿，批量解析需要已认可的粒度和指定范围。

## 收录、存档与状态

- 只收录用户明确给出的材料。新链接进入“项目与文章”，保存原始 URL、来源类型、接收日期与备注，标为 `pending`（待解析）；类型允许扩展。
- 相同链接检查是否已有条目，合并备注并保留原内容。标题能核实才填写；无法读取时使用明确的暂定标签并解释，不根据链接猜正文。
- 原始来源链接与原件同时保留。PDF 是内容快照，动图、视频和外链可能缺失；记录捕获日期、完整性和缺失项，不能把 HTTP 200、验证码页、标题或部分图片当作取得完整文章。
- 本地原件存档后运行 `npm run verify:archives` 核对真实文件。公开部署仅验证存档记录的格式，无法检查这台机器上的私有原件；本地保存也不代表已经完成异地备份。
- 完整 PDF、截图或网页原件放在 `.pocket/<source-id>/`，保持原件格式并在条目中关联；该目录不进入公开 Git 与网站。只有确实取得文件才标记“存档已保存”，实际核对正文和图片后才能标记完整性已核对。文件未取得时保持“待存档”。
- 收录、存档与解析是独立状态。单条 AI 解析后为 `draft`（待校准）；用户明确认可本条内容后为 `reviewed`（已认可）。认可 Skill 不等于认可每一条输出，批量结果默认仍是 `draft`。

## 三层拆解

**项目与文章**：说清它是什么、面向什么场景、解决什么问题及希望达到什么目标；保留外部来源链接。

**关键设计**：提炼实现目标所依赖的关键安排——职责怎样组织、链路怎样连接、状态怎样协调，以及理由、取舍和适用条件。功能名称和依赖清单不能替代设计解释；名称应表达可以理解、组合和迁移的思路。

**技术与原理**：解释支撑所选设计的具体技术与关键机制——叫什么、怎样工作、为什么支持这个设计、有哪些限制。只提取与所选设计相关的技术，不为了凑齐层级罗列全部依赖。

设计与技术可跨来源复用；新增前检查已有条目的含义和条件，不仅凭名称相同合并。只维护“来源→设计、设计→技术”两组关联，出处与反向关联由构建生成；二、三层通过第一层追溯来源。

## 证据、粒度与修订

- 项目依据实际 README、核心源码和配置，文章依据完整原文与图示；图文材料先确认图片能读取。证据不足的条目保留待解析并记录缺失，不能补造设计或原理。
- 区分原文明确说明、源码直接体现和 AI 推断。记录证据位置（来源 ID、章节、源码路径或 PDF 页码）；实现存在不代表效果已验证，作者主张不自动成为普遍结论。
- 先选核心设计，以理解和复用所需的信息为准，不设固定条数或字数。每个块有一句简述；详细机制、取舍与证据留在同一份 Markdown 正文，避免维护两套重复的人读与 AI 读内容。
- 太粗时补足设计动作、原因或机制，太细时删掉无关实现细节；不要机械压缩到固定字数。用用户指定的一条真实素材校准：设计选得是否合适、名称是否准确、解释是否太粗或太细。
- 单次内容修正先作用于本条。用户认可通用表达习惯时再更新 Skill；当前还没有已认可的粒度样例，不能宣称 Skill 已校准。

## 完成一次任务

按实际授权范围保存、构建与发布，遵守仓库规定的提交身份。已有网站发布授权适用于本项目的收录展示，不扩大为公开原件或自动生成最佳实践。批量只处理用户指定的待解析范围，逐条保留成功、证据不足和访问失败结果；最佳实践是未来输出，普通素材拆解不自动生成最佳实践文章。

简短交代收录了什么、哪些已经存档或解析、哪些仍缺材料。分别核对文件保存、构建、提交推送、部署和可见效果，不用其中一个代替其他状态。
