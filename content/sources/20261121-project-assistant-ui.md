## 问题与目标

一个能调用工具的 Agent，并不等于一个好用的产品。回答可能逐段生成，工具参数可能尚未齐全，执行还会遇到等待、确认、失败和重试。如果前端只是把后端文本贴进聊天框，用户很难知道系统到底进行到哪一步。

assistant-ui 提供可组合的对话界面基础。它把界面、运行时和后端分开：界面负责显示与操作，运行时整理消息和交互状态，后端负责生成内容与执行任务。这样接入不同 Agent 后端时，可以保留大部分交互结构。

## 方案怎么做

消息列表、输入框、工具结果等被拆成可组合的组件，通过共同的运行时读取状态和触发操作。开发者可以调整布局与样式，不必把消息分支、编辑、重新生成等行为都塞进每个视觉组件。

运行时有不同的接法。若让它管理本地会话状态，就按相应接口接入模型与工具；若已有外部状态或 Agent 框架，就通过适配器把外部消息和事件转换成界面能理解的结构。选择的关键是谁拥有真实状态，避免前后端各维护一份互相矛盾的进度。

工具调用不只显示一个“执行中”。参数仍在生成、参数已经完整、需要人工操作、工具返回结果以及异常中断，需要区别表达。参数的整体状态和字段状态还可以分别使用：某个字段已经完整，不意味着整份参数都已准备好。

例如一个转账工具可以先预览正在形成的收款信息，参数齐全后展示确认内容，再等待服务端执行结果。用户在界面点了确认，只代表提交意愿；是否有权限、金额是否有效以及操作是否成功，仍必须由实际执行端判断。

它还提供按工具类型渲染结果的方式，让表格、进度或业务组件进入对话。这样用户看到的是任务过程与结果，而不只是模型写的一段说明。代价是需要为关键工具定义稳定结构和组件，后端事件也必须能够区分各阶段。

## 适用条件与取舍

适合已有模型或 Agent 后端、希望把交互做成产品的 React 项目。它减少界面与状态衔接的重复劳动，却不会替你生成完整的业务服务。会话持久化可以接自己的数据库或相应服务，并非使用界面库就自动获得可靠存档。

最值得借鉴的是让显示依赖明确状态，而不是猜测文本含义。接入时要核对适配器是否保留工具标识、异常和中断等语义，并根据真实状态提供重试入口。组件库采用 MIT 许可；选用额外服务或其他依赖时，仍需单独判断其条件。
