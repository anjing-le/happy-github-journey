## 问题与目标

调整一段提示词后，几个示例可能明显变好，却在其他输入上退步。模型还有波动，只靠人工临时提问，很难保留比较依据，也难以解释上线前到底检查了什么。

Promptfoo 把测试输入、候选方案和检查规则分开配置，再批量组合执行。它可以比较提示词与模型，也能把检查目标接到应用或 Agent 上，核心是让质量评价从一次试用变成可重复的工程过程。

## 方案怎么做

案例定义输入变量、参考结果与判定条件，候选配置指定提示词和调用方式。运行后逐一比较案例与候选的组合，既能看到总览，也能追到某条输入具体失败在哪里。这样替换一个模型时，不必重新手动整理全部问题。

检查规则有不同层次。结构、包含关系、数值和明确业务约束可以用确定性的断言或代码检查；需要理解语义的部分，再使用评价准则或模型评审。两类判断分开，便于解释到底是格式违规、调用异常，还是回答质量不足。

模型评审需要校准。先确定标准和反例，再用人工核对的案例观察偏差，比较答案时也要注意位置和文风影响。把一个模型接成评审器，只是得到一套判断流程，还没有证明它符合自己的业务目标。

对有波动的生成任务，可以重复执行并观察关键场景表现，同时记录模型、采样配置与缓存情况。命中缓存能节省时间和费用，却不等于重新采样，不能用相同缓存响应证明模型稳定。

结果可以导出并接入持续集成。是否阻断发布要明确配置：调用错误、断言失败和关键场景退步分别怎样处理。只运行命令、生成报告，并不会自动形成有效门槛；总体平均分也不应覆盖某个关键权限或安全要求的失败。

## 适用条件与取舍

适合已有可重复任务，准备持续修改提示词、模型或 Agent 的团队。案例应来自真实需求、故障与边界条件，并与日常调优材料适当分开；如果每次只针对固定测试答案优化，很容易得到只会应试的方案。

本地运行评测器不代表所有输入都留在本机，数据仍可能发往配置的模型服务；调用成本和敏感数据需要按实际配置管理。红队测试可以帮助发现问题，但测试通过只覆盖相应范围，不是完整安全证明。项目采用 MIT 许可。
