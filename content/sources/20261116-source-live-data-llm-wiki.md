## 问题与目标

数据团队的知识通常藏在建表语句、加工任务、文档、接口和看板里。只知道字段名，未必知道它怎样计算；同名指标也可能采用不同口径。把这些材料直接放进检索系统，可以改善查找，却不会自动消除矛盾、过期内容和缺失依赖。

LLM Wiki 的思路是在查询之前先加工知识：把源材料整理为结构统一的页面，保留依据，明确对象之间的关系，再供 AI 检索、选表、生成 SQL 和分析变更影响。这里的“编译”是对分阶段加工与校验的类比，知识是否正确仍需要证据和判断。

## 方案怎么做

先区分长期知识与即时信息。表结构、加工逻辑和业务定义适合提前整理；当前数据、任务日志和监控结果在使用时通过工具获取。材料按可用、待治理、已弃用分开放，只让符合要求的材料进入生成。例如分析一张加工表，既要有字段定义，也要有产出任务代码，否则只能知道它长什么样，无法解释怎么算。

再统一页面契约。每页上方用结构化字段保存类型、来源、所属业务域和上下游，正文解释背景、加工逻辑、字段及使用条件。生成、建图、检索和校验工具都遵守同一份 Schema，不必各自从自然语言里猜关系。任务代码帮助核对实际计算，文档补充业务意图；两者冲突时，还要确认代码是否对应当前运行版本，不能把已有实现直接等同于正确需求。

生成过程分开处理事实和判断。基础页面先只写源材料支持的内容，暂不猜所属业务域等字段；等基础信息齐备后，再产生分类、指标归并等候选，由人确认。脚本检查字段是否真实存在、页面结构是否合法；语义是否准确、口径是否合理则需要模型评审和人工复核。这样能把格式问题与业务判断分别处理，但不能靠格式校验保证全部内容真实。

构建按依赖推进：先生成表、接口等基础页，再聚合出业务域、指标和全局入口，最后建图并做健康检查。协调层只安排阶段、等待确认和汇总结果，各阶段通过约定文件交换产物。独立对象可以用隔离上下文并行生成，聚合步骤必须等前置产物就绪；页面级检查和全局数量、链接、关系检查共同决定是否发布。

知识同时按树和图组织。业务域构成树，让 AI 从全景逐层缩小范围；上下游、指标来源、看板消费等关系形成图，用于跨对象查找。关系从页面字段统一生成，反向依赖按规则计算，供全局遍历或回填到单页使用。当前规模采用文件与 JSON 即可，不必先部署图数据库；这些派生信息仍要随页面变更一起重建和核对。

查询先分类型：表名明确就读详情，问上下游就沿关系遍历，模糊问题才走完整搜索。模糊搜索先选相关业务域，再结合域内资产与关键词产生候选，沿血缘补充相关表，去重后读取候选详情。能否覆盖需求是第一关，通过后才比较相关性和复用价值。例如统计不同主播等级的开播次数，要同时找等级信息与开播记录，并区分已有固定时间窗口和自定义日期的计算方式，不能只凭表名相似就推荐。

改数据模型时，这些知识继续支撑一条工作流：明确变更含义，查表与下游，读取相关 SQL 判断业务风险，再生成改造、验证和回滚脚本。新增字段是否传播到所有下游、切换数据源是否改变阈值判断，都需要人确认。状态文件保留各阶段结果，便于回查和续跑；生成了 SQL 只是交付的一部分，执行与结果核验还要另外完成。

维护时，对比源材料、已有页面及来源记录，只重做受影响的页面和聚合步骤，再重建关系、检查整体一致性。持续检查断链、无效节点和结构变化，把问题送回对应阶段修复。局部生成节省模型调用，但全局索引和检查仍有随总规模增长的成本。

## 适用条件与取舍

适合资产较多、依赖关系重要、业务口径会变化，而且能够取得可靠源材料的数据团队。它把一部分成本前移到采集、结构设计、生成与审核阶段，换取后续查询的可理解性和复用机会；材料覆盖不足、域分类错误或更新不及时，都会限制答案质量。

Wiki 与 RAG 可以组合：前者整理语料，后者在查询时找依据。当前检索主要依靠业务域、关键词和关系图，向量检索属于补充规划；任务与看板清单的扩展、自动检测源变更以及系统化评测也仍需继续建设。支持局部重跑，并不等于已经实现自动保鲜。

关系图只能遍历已知且正确的边，结构检查也不能发现所有业务错误。部分示例报告了查询和生成提效，但缺少足够的测试范围与重复测量信息，不能据此推断任意团队都能零遗漏或获得固定倍数收益。真正采用时，仍要用代表性问题检查选表、召回、答案和生成 SQL 的正确性。
