## 问题与目标

协作看板和任务列表经常要显示其他人刚刚修改的数据。反复请求全量列表浪费传输，也让界面等待；只订阅新增事件又不知道完整起点，断线重连后还可能漏掉变化。

Electric 的同步引擎从 PostgreSQL 捕获变化，把应用需要的部分数据送到客户端。这里重点是数据库到客户端的读路径：前端维护可持续更新的数据视图，写入仍通过业务服务或选定的写入方案处理。

## 方案怎么做

Shape 用来描述客户端要同步的数据范围，例如某个项目下的任务。服务端为该范围建立数据状态和变化日志，客户端先获取初始内容，再从给定位置接着读取变化，而不是每次重新查询全部记录。

同步需要明确的进度协议。初始内容可能分多次返回，客户端根据 offset 继续读取，并用服务端的控制消息判断是否已经追上当前状态；进入实时阶段后，可以继续用长轮询或相应的事件流接收更新。一次响应结束并不代表所有数据都到了。

客户端保存同步标识和日志位置，以便继续获取。如果服务端要求重新拉取，就清除相应的旧状态并重新同步。可恢复的连接与可恢复的数据状态是两回事，只有重新连上网络，不足以说明本地数据仍然完整。

例如用户修改任务名称，可以先在界面显示临时结果，再向已有 API 写入。业务服务验证并提交后，正式数据通过同步通道回来，客户端将临时状态与权威结果对齐。乐观更新缩短等待感，但失败回退、重复提交和业务冲突仍需处理。

同步范围也必须与权限绑定。浏览器提交的表名或过滤条件只是请求，受信任服务应先验证身份，再确定允许的范围；可以代理请求，或提供与范围绑定的访问凭证。使用缓存分发时还要防止不同权限范围串用数据。

## 适用条件与取舍

适合界面高度依赖共享数据、持续更新和低等待感的产品。它减少应用逐条拼接推送消息的工作，但不会自动提供完整的双向离线冲突处理，也不会把前端所有写入变成已确认事务。

数据已经下载后，撤销权限不会让用户忘记这些内容，因此需要明确后续下载、凭证与本地缓存的处理策略。同步引擎还增加日志、状态维护和复制运维成本。项目已转到 Neon 组织，此处按固定版本学习同步部分；该部分代码采用 Apache-2.0 许可。
