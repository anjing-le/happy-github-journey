## 问题与目标

当 Agent 已能独立完成不少单项工作，新的负担变成了人要同时盯住多个会话：哪个任务做到哪里、群聊中的新要求是否传到了代码评审、机器离线后还能不能接着做。把所有工作塞进一个会话容易阻塞和混淆，完全拆散又失去统一的上下文。

Super-agent 探索的是一种持续在线的协作架构：让人始终面对同一个助手，底层负责并行执行、跨渠道衔接、主动响应和异常恢复。它承接的是任务之间的组织问题，具体实现仍处于原型探索阶段。

## 方案怎么做

先分开协调和执行。常驻的 Router 层掌握整体情况，承接人类交互、分派任务和汇总结果；Worker 在隔离的上下文里使用工具完成具体工作。Router 尽量保持轻量，不亲自跑耗时任务；Worker 可以在内部继续拆解，但不各自向群聊输出过程。这样用户不必手动管理每个底层会话。

再让环境变化驱动工作。群聊消息、代码评审意见和检查结果都变成事件，先用来源、群组等明确规则过滤，再让模型判断候选事件是否值得介入。新话题由 Router 分派；任务一旦订阅了相关话题，后续事件便直接进入对应 Worker。比如群聊提出需求后生成了代码评审，同一个 Worker 可以同时订阅两处，继续处理新的要求，并把结果交回 Router 统一回复。事件直通减少重复转发，但不等于多个 Worker 已经自动解决了修改冲突。

全局协调也不必一次装下所有历史。当前输入只带摘要、相邻信息和关联标识，较长内容保留在窗口之外。需要时，从当前消息找到话题、再找到任务和相关代码评审，沿关系逐步回读。Router 忙碌期间积压的事件还能合并到下一轮处理，用一次判断分摊部分开销；窗口容量和判断准确度仍限制批量大小。

对耗时工具采用异步执行：启动后先返回“已启动”，完成后再以事件交回结果，并提供停止入口。用户的新要求可以在当前推理步结束后被处理，不必一直等后台任务结束。对外呈现也随渠道调整：群聊给简短结论和需要决定的问题，代码评审或文档承载具体改动与验证信息。系统还可以在约定范围内提前准备，例如先复现问题或起草回复，有价值时再交付；这会消耗额外算力，也需要明确可执行范围。

为了长期运行，把三件事拆开：推进 Agent 的计算进程可以替换，会话与任务状态独立保存，真实仓库和工具则留在原设备，通过轻量端侧进程执行命令。云端可以继续协调，但依赖离线设备的操作仍需要等待。最后由主流程之外的 Watchdog 周期性巡检，既看服务是否正常，也看任务是否在朝目标推进，发现停滞后再介入恢复。

## 适用条件与取舍

这套安排适合个人或小团队同时推进多个相对独立的任务，并且愿意共享一定范围的上下文。多会话维护会增加 token 与状态管理成本；任务高度耦合、规模扩大或信息必须隔离时，协调层如何拆分、谁能读取哪些历史，都需要重新设计。

初步合成负载实验支持两个有限结论：明确分工比完全依赖模型临时决定是否委派更稳定；订阅直通主要减少协调开销，在该负载下并未明显改善完成时间。实验用等待工具代替实际编码，因此不能据此推断代码质量或所有业务场景的收益。

长期记忆、用户中途接管、跨实例协作和安全仍有开放问题。尤其是云端持续读取外部消息，又能操作多台设备时，提示词注入或服务入侵可能扩大影响范围；本地凭据也可能被工具带入上下文。接通环境与保持在线只是基础，权限、凭据隔离和真实任务验证仍需单独落实。
