## 问题与目标

一个 Agent 的表现不只由模型决定，还取决于工具、提示词、上下文和执行环境。如果训练时把它改成简化的问答程序，即使分数上升，也可能没有学会真实工作中的多步判断。

Agent Lightning 的核心是保留真实执行流程，在模型请求边界采集交互，再把任务结果变成训练信号。优化目标是模型策略，工具与运行流程仍参与训练环境；它需要可训练模型与相关资源，不能把任意闭源 API 的调用记录直接变成对该模型的训练。

## 方案怎么做

架构分成训练器、API 网关和执行控制器。训练器创建任务、提供当前模型并更新参数；网关代理模型请求，按执行标识记录交互；控制器在本地进程或 Kubernetes Job 中启动 Agent，持续核对排队、运行和结束状态。任务执行与 GPU 训练资源由此可以分开安排。

每个输入可以运行多次，产生多个 rollout。它代表一次真实任务执行，不等于一条已经可用的训练样本。一次执行里可能调用模型多轮、使用工具并遇到错误；网关把这些模型交互与同一执行及重试关联，任务侧再报告奖励，训练端整理后才能更新模型。

采集不只保存可读文本，还需要实际 token 序列、生成概率等训练信息。只有前后调用的 token 历史确实连续时才合并，工具响应和提示模板造成的不连续不能靠文本看起来相同就抹掉。兼容的请求接口减少对 Agent 的修改，但推理后端是否提供所需字段、模型与采样配置是否一致仍需要核对。

代码任务给出了完整例子：为每题准备相应仓库与依赖，在独立环境里修改代码，运行原先失败和原先通过的测试，再产生奖励。题目还按有效性、执行成本和试跑难度筛选，既保留可学的混合难度任务，也保留一部分困难题，避免只在容易题上得到好看分数。

奖励本身需要保护。若 Agent 能查看隐藏修复、从网络下载原始答案或修改验收代码，就可能拿高分却没有解决问题。工作区隔离、命令限制与出口网络策略需要配合，测试结果由环境计算，不能用 Agent 自述替代。训练任务与验证任务分开，防止把记住题目当成泛化能力。

## 适用条件与取舍

适合已有实际 Agent、稳定任务与验收方式，并准备投入模型训练资源的团队。若主要困难是需求不清、工具不稳定或奖励不可信，应先修这些环节；更多训练可能只把错误信号放大。

保持真实流程减少训练与部署脱节，也把工具成本、环境故障与多轮数据处理带进训练。进程执行成功、轨迹采集成功、训练完成和业务能力提升分别验收；示例任务中的收益不自动代表自己的场景也会获得相同提升。
