## 这篇文章要解决什么问题

同一模型、同一提示词、同一软硬件环境，关掉随机采样或固定 seed 后，为什么并发请求一多，回答仍可能变化？作者在 vLLM + Qwen3-8B 的测试中观察到：没有其他请求时重复调用，输出可以一致；和其他请求一起组批时，一致性可能被打破。

这里需要区分两个目标：重复运行得到同样结果，叫运行间确定性（Run-to-run Determinism）；同一请求无论和谁一起算、批次有多大，都得到一致结果，叫批次不变性（Batch Invariance）。后者适用于需要可复现生成轨迹的强化学习 Rollout，也关系到推理系统的调试与结果对照。

文章的范围主要是数值计算和执行调度。在输入、权重与采样条件固定后，继续追踪动态组批如何影响底层计算。依据：PDF 第 1–2 页。

## 先看整篇的推导路线

并发请求改变批次与输入形状 → 推理引擎为提高性能选择不同的算子配置 → 同一输出的求和分组或合并路径变化 → 浮点舍入差异 → 可能影响后续 token 选择。

作者沿着这条链，从浮点数讲到 GPU 分块计算，再分别检查矩阵乘法、归一化、Attention、编译生成的内核和跨 GPU 通信。关键问题始终是：**批次变化有没有改变同一输入内部的计算与合并结构**？

## 1. 根因：数学等价的求和，数值结果可能不同

浮点数使用有限位数保存数值，计算结果写回时可能舍入。因此，先算 `(a+b)+c` 和先算 `a+(b+c)`，结果不保证相等。文章用 FP16 的例子说明：按最近偶数规则逐步舍入时，`(2048+1)+1` 得到 2048，`2048+(1+1)` 得到 2050。

这解释了为什么一个请求的上下文没有被其他请求污染，结果仍可能受组批影响：变化发生在计算安排上。需要关注的“归约结构”，就是一组值怎样分段求和、各段由谁计算，以及局部结果怎样合并。

文中的 FP16 例子用于解释机制；实际 GEMM 可以用 FP32 累加，不能据此把全部问题归因于 FP16 存储精度。更高精度也不能自动消除分组变化的影响。依据：PDF 第 2–4 页。

## 2. GPU 为什么会改变计算安排

文章先讲性能优化，是为了说明这些安排为什么会动态变化。GPU 的计算单元需要持续获得数据；反复从全局显存读取相同内容，会浪费带宽，等待数据又会使算力闲置。

### 分块和缓存复用

矩阵乘法 `C=A×B` 中，每个输出元素都沿公共维度 K 累加乘积。Tiling 把矩阵分成小块，让一个线程块（CTA）负责一个输出块：将所需数据从全局显存搬到共享内存，再供线程读取、计算；中间累加结果留在寄存器，完成后写回。这样同一份数据能被多次利用。

Swizzle 进一步调整不同输出块的访问顺序，使处理相邻块的任务更有机会复用 L2 缓存里的数据。这是不同存储层级上的复用思路。依据：PDF 第 5–10 页及分块、存储层级图。

### 任务太少时，拆分同一个求和任务

当输出矩阵的 M、N 很小而 K 很长时，仅按输出块分配任务，可能无法让足够多的 GPU 计算单元忙起来。Split-K 把同一个输出的 K 维点积拆给多个线程块，各自算局部和，再合并。

合并可以使用原子加，也可以先把局部结果写进临时空间（workspace），再启动一个归约内核。后者即使在固定拆分下每次有序合并，一旦批次导致拆分段数变化，求和分组仍可能变化。依据：PDF 第 8–10、17 页。

### 重叠搬运与计算，并在资源预算内调优

多级缓冲让当前块计算时，下一块的数据提前异步搬运，以减少等待。增加流水线级数会占用更多共享内存和寄存器；扩大分块也会扩大累加器，资源不足时可能发生寄存器溢出或降低驻留并发。

因此，分块大小、warp 数量、缓冲级数需要组合考虑。CUDA 的线程编程、Triton 的块编程与 autotune，都是组织或选择这些执行安排的手段。原文的寄存器/共享内存公式用于估计预算，具体最优配置仍取决于内核与硬件。依据：PDF 第 11–16 页。

## 3. GEMM：要固定哪一部分，得看真实内核

性能配置要分开判断。调整独立输出块的任务映射、改善缓存访问，不一定改变某个输出元素内部的累加；改变 K 维拆分和局部和合并，则可能直接改变归约结构。

原文第 17 页先从参数层面区分这些影响，第 20–21 页又补充了更细的条件：外层 `BLOCK_K` 变化，不一定改变底层 warp 或矩阵乘加指令的实际累加步长。最终需要看硬件、精度和所选内核，不能把一个参数名称当成所有实现的保证。

文章所述 vLLM 路径采用多种办法：

- FP16/BF16 的 Linear 可路由到定制 Triton 矩阵乘法，使用固定配置、不按形状重新 autotune，并且内核没有实现 Split-K。
- 裸 `torch.mm` 等入口与 Linear 不一定走同一路径；文中分别讨论了 SM80 的算子覆盖和 SM90/SM100 的 cuBLASLt 限制方案。
- 低精度 FP8/FP4 又可能进入 CUTLASS 等实现。FP8 的 workspace 限制是间接约束，原文也注明它缺少显式 reduction-mask 的 API 级保证；FP4 示例则固定配置并检查调度器不拆 K。

另外，`persistent` 描述线程块持续处理多个输出块的调度方式；文中的确定性主要来自固定的累加配置与不拆 K，不能只凭函数名认定结果确定。依据：PDF 第 17–25 页。

## 4. RMSNorm：每个 token 独立，也可能被批次间接影响

RMSNorm 对每个 token 的隐藏向量求平方均值，再用均方根缩放，并乘逐维权重。不同 token 可以独立处理，通常一个 token 对应一个线程块。

问题出在性能调度：文中 CUDA 实现会根据 token 数量选择不同线程块大小。线程数一变，每个线程负责累加哪些元素、线程块内部怎样合并局部和，都可能变化。于是“行之间独立”还不足以保证“同一行始终按同样方式求和”。

文中批次不变模式通过固定归约宽度等办法，使同一 token 的内部计算不随 token 总数变化。有 residual 的融合 CUDA 路径和没有 residual 的 Triton 路径采用不同实现；Triton 的逻辑 `BLOCK_SIZE` 也不能直接当作 CUDA 线程数。依据：PDF 第 26–32 页及分发矩阵。

## 5. 编译：入口被修好，最终执行仍可能变

`torch.compile` 可以捕获计算图、融合操作，并由 Inductor 生成内核。原文展示，编译模式可能绕过 eager 模式的自定义算子覆盖，RMSNorm 进入原生表达式，再由编译器生成 Triton 实现。

编译器也会优化归约。当一行很长、可并行的行数很少时，Split-Reduction 可以把同一行分给多个任务，再合并。这和 Split-K 面临相似的数值问题。

文章讨论了动态形状代表值、编译区间和拆分启发式之间的关系：标成动态形状，并不代表形状不会参与配置选择。文中 `hidden_size≤8192` 不拆分的条件、预编译图的数量和派发方式，均绑定它分析的软件版本与编译配置。

因此要沿着“算子入口 → 分发 → 编译/融合 → 最终内核”核对，并比较不同批次下的实际结果。依据：PDF 第 29–36 页。

## 6. Attention：分查询与分 KV，是两件事

对每个查询向量，Attention 要与相应的 Key 计算分数，做 Softmax，再对 Value 加权求和。FlashAttention 以分块方式融合这些步骤，使中间分数和概率尽量留在片上存储，沿 KV 序列逐块更新归一化信息和输出。

沿查询轴分块，主要决定哪些查询一起计算；沿 KV 轴拆分，则把同一查询需要汇总的内容交给多个任务。Decode 阶段查询很少而历史 KV 很长，FlashDecoding 用 Split-KV 增加并行，再合并各段的局部输出与归一化信息。拆分段数随批次变化时，合并结构就可能变化。

Chunked Prefill 在调度层切分查询 token，它本身不要求不同查询块互相求和；但 chunk 大小改变内核输入形状，又可能间接影响 Split-KV 的选择。因此还需检查 KV 侧的计算安排。

文中 vLLM FlashAttention 路径在批次不变模式下使用 `num_splits=1`，代价是小批次 decode 的并行利用率可能下降。依据：PDF 第 36–41 页及查询轴/KV 轴图示。

## 7. 多卡：各卡算得稳定，合并过程也要稳定

Tensor Parallel 把模型计算分到多张 GPU。文章用“列切分 → 行切分”的配合解释怎样减少中间通信：第一层保留各卡的独立输出分片，下一层在本卡继续计算局部贡献，最后通过 AllReduce 求和，让各卡得到完整结果。依据：PDF 第 41–43 页及两层矩阵切分图。

AllReduce 自身也有性能选择。消息大小随 token 数变化，NCCL 可能选择不同算法、协议、通道数量和数据分区。即使仍叫 Ring 或 Tree，不同通道也可能具有不同的归约路径；某个元素随分区边界变化进入另一通道，就可能经历不同的加法顺序。

vLLM 的 Custom AllReduce 等低延迟快路径也有自身的算法选择。原文所述模式先收窄候选通信路径，再约束 NCCL 的算法、协议和通道，避免单卡已经稳定的结果在跨卡合并时再次出现波动。约束通信策略会影响吞吐和拓扑适应能力。依据：PDF 第 43–47 页。

## 这篇文章可以留下哪些设计判断

以下是从原文归纳的可复用思路，具体条件和机制在第二、三层展开：

- **按存储层级复用数据**：让计算块与缓存容量、数据访问顺序配合，减少重复搬运。
- **让数据搬运与计算重叠**：用异步流水线减少等待，并在寄存器和共享内存预算内选择缓冲规模。
- **跨卡先独立计算，再合并**：组合列切分与行切分，使连续计算保留分片，延后通信。
- **固定单条输入的求和结构**：保持同一输入的内部累加与合并稳定，同时保留独立任务的并行。
- **沿实际执行路径落实约束**：覆盖硬件、精度、入口与编译后的不同实现，验证最终执行的内核。
- **固定跨卡的合并路径**：单卡与多卡作为一条计算链核对，控制可能改变求和的通信选择。

这些思路之间有关系：前三条解释性能如何获得、为何需要取舍；后三条约束会影响数值一致性的执行变化。文章没有给出本项目可直接采用的通用最优配置，性能代价与效果需要在目标环境测量。
