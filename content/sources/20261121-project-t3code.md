## 问题与目标

编程 Agent 的能力越来越强，用户的工作却仍分散在终端、聊天、审批和 Git 界面里。离开电脑后，任务可能等着一次确认；换到手机，又不知道它运行在哪台机器、改了什么、是否真的完成。

T3 Code 提供一个共同的控制界面，让已经安装并登录的编程 Agent 继续在工作区所在机器运行。桌面、网页和手机连接同一个服务，用户围绕线程查看过程、批准操作和审查代码，不需要把所有工具重写成另一套 Agent。

## 方案怎么做

先守住执行归属：仓库、终端、Git、Agent 进程和相关凭据属于服务端环境，客户端负责展示与控制。手机连到某个工作环境后，请求就在那里的工作区执行；目标环境不可用时，不能悄悄改用手机自身或另一台服务的状态。

不同 Agent 放在适配层后面，将其消息、工具事件、审批和运行状态转换为共同协议。上层可以提供统一体验，但适配层仍需表达能力差异：某些权限模式、原生恢复或会话回退并非每个 Agent 都支持，同一个按钮名称不能保证底层语义完全一致。

服务端先决定状态变化，再执行外部动作。事件、持久化查询状态、指令回执和待执行动作在同一数据库事务里保存，提交后由后台执行器调用 Agent 或文件系统。客户端收到接收回执，只表示意图落地；模型回合结束、检查点生成和其他收尾又是不同进度，分别展示才能避免提前宣布完成。

跨端连接也有共同归属。每个环境由共享运行层管理连接、退避重试与缓存，界面不各自重复重连。套接字已经打开，不代表配置和线程数据已同步；离线时可以展示缓存，恢复时用序号和快照接续，避免较旧请求覆盖更新结果。历史事件会清理，超出重放范围需要重新取快照，不能假定事件日志永久保留全部历史。

代码工作通过分支和 worktree 组织，使多个线程能够各自修改与审查。检查点用隐藏 Git 引用记录工作区，不往用户分支额外堆提交。撤销文件还要与 Agent 会话协调；若底层 Agent 无法回退对应对话，就应先拒绝不完整的撤销，而不是只恢复磁盘后让对话继续沿用旧理解。

例如桌面启动一次改代码任务，手机收到确认请求后允许继续，随后查看差异，再决定是否提交。任务始终在原来的服务环境执行；手机展示的是同一任务状态，确认的是具体请求，Git 提交则是独立的后续动作。

## 适用条件与取舍

适合已经使用多个编程 Agent、需要跨设备协作或集中审查代码的人。前提是执行环境在线、目标 Agent 可用、网络与认证路径正确；界面统一无法替代底层工具安装和权限管理。

可靠控制界面需要投入状态持久化、协议兼容、断线恢复和能力适配。后台动作依赖的进程消失后，部分动作不能直接重放；工作区隔离也不等于安全沙箱。使用时应分别判断接收、执行、收尾和代码验收，不把流畅的聊天体验当成任务可靠性的全部。
