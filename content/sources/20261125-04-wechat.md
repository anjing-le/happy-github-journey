## 问题与目标

设计 Agent 难在持续符合某个业务的风格与规则，也难在把生成结果可靠地修改和交给研发。把网页转成设计工具节点，布局、组件和交互容易损失；反复让模型重写，又可能把刚调好的细节改坏。

TaoDesign 的方向是让设计产物直接成为可运行、可编辑的网页，再把业务经验组织成能检索、能确认、能迭代的资产。设计质量、工程稳定性和研发交接共同决定它能否真正被使用。

## 方案怎么做

早期通过 MasterGo 插件把受限的 HTML、Tailwind 内容解析成设计节点。格式互转和逐节点工具调用带来损耗与开销，于是改用浏览器作为画布，直接生成 HTML 或 JSX，保留网页的布局和交互能力。继续对接设计工具时仍要面对格式差异，切换画布并没有消除所有交接成本。

桌面端承接对话、画布、轻量原生入口和本地交互，服务端负责身份、项目权限、调度、持久化与事件续传，云端沙箱运行 Agent 和页面环境。计算环境可回收，长期状态另行保存。画板移动、缩放属于展示状态；改文字、尺寸和样式才涉及页面源码，这两类操作分开管理。

页面修改先进入队列，依据最新源码定位并检查冲突，简单变更由程序生成补丁；定位失败或意图复杂时再交给 Agent。成功后统一保存、同步运行环境并清理待办，冲突则保留等待处理。历史版本也独立管理：生成结束后异步保存文件快照与清单，恢复时检查当前基线、取得排他操作权并先保存安全快照，避免回退覆盖正在发生的修改。

风格资产不仅是颜色和字体，还包括组件与布局模板、图片等素材，以及业务规则。参考页面和文档先被整理为可编辑草稿，设计师确认适用业务、条件与版本后再发布。一次活动页的视觉特点，不会自动成为所有页面的通用规范。

消费这些知识时，先按页面与任务批量召回，再组织给生成链路使用。离线提取要保留默认值、适用条件、例外和状态联动；在线主要负责选择与检查覆盖，选定后由代码组装，减少再次自由改写造成的条件丢失。压缩有助于节省调用，但少了关键条件，生成再快也会用错规范。

质量改进从标准案例和真实失败案例出发，保留提示、输出、工具调用与人工判断。模型评审经过设计师标注校准；失败先区分工程调用问题和资产缺口，再选择修工具或起草规则。用户不满意、反复修改只是排查信号，须排除需求变化和个人偏好，经设计师确认、回归验证后才更新正式资产。

交接也不只交一张图：页面的不同状态、跳转和触发条件形成关系，补充节点注释，并把相关材料交给研发读取。注释与代码分开保存、关联具体页面元素，页面变化后需要核对锚点。这样设计与研发可以围绕同一份状态和验收依据讨论，后续实现、测试与部署仍有各自责任。

## 适用条件与取舍

适合已有业务设计规范、能持续提供设计评审，并且希望连接原型与研发的团队。直接使用网页提高可运行性，也要求维护源码编辑、运行隔离、快照和知识版本，工程成本不会消失。

现阶段已经有生成、编辑、资产和基础交接的实践，团队推广与动态自动验收仍在推进，不能把完整“一人团队”写成既成能力。工具耗时下降与知识调用减少也不等于用户体验自动变好，需要同时检查关键规则覆盖和实际交付质量。
