## 问题与目标

Agent 一旦能运行命令、改文件或操作浏览器，任务就不再只是生成文本。直接放在开发机上执行，会把个人文件、依赖、网络和任务状态混在一起；改成集群部署，又可能需要重做环境管理和调用接口。

OpenSandbox 把执行环境本身做成独立能力：应用请求创建一个有资源、时限和访问规则的沙箱，等它就绪后调用命令、文件或其他工具，最后回收。SDK、命令行和 MCP 接入共同契约，具体运行在容器还是轻量虚拟机由后端承担。

## 方案怎么做

控制面负责身份、生命周期和端点，执行面提供沙箱里的实际操作。服务通过统一接口接入 Docker、Kubernetes 及模板化的 Fast Sandbox；后者在 Kubernetes 路径中组合轻量虚拟机能力。对上保持共同的请求形式，同时把不同后端的能力差异留在明确边界内。

状态必须跟真实工作负载核对。创建先返回准备中，客户端继续等待运行和所需服务就绪；到期时间使用明确的绝对时限，暂停或服务重启不会自动续命。暂停后恢复是一类操作，已经退出的工作负载则需要替换，不能都包装成同一种恢复。

回收也分阶段。删除接口接受请求，不等于容器或进程已经消失；某些池策略还会保留运行资源。控制面只持久化自己拥有的记录，例如模板目录和快照元数据，容器、Pod 或运行时资源才是实际工作负载的依据，避免另维护一份看似权威却已经过时的状态。

执行边界由运行时和网络共同落实。出口组件可以按沙箱限制域名、地址和端口，DNS 过滤与网络层拒绝各有职责；策略没有安装成功时不能先把沙箱当作已受控。收紧规则时要检查已有长连接，避免只有新请求被拒绝，旧连接仍能继续使用。

例如让 Agent 修复一个仓库，可以从准备好的镜像创建环境，只挂载需要的文件、分配资源并开放必要模型地址。任务结束后分别检查运行结果、产物保存和资源回收。换到集群时应用仍使用同一层生命周期接口，但隔离、网络与存储条件必须重新核对。

快速创建依赖模板和预热资源，把环境准备移到任务之前，而不是每次从零配置。这样换来更短的启动路径，也引入镜像、模板版本、池容量、快照兼容和故障清理等维护工作。性能数据只能在相应环境与测量口径下理解，不能直接套到自己的部署。

## 适用条件与取舍

适合代码执行、浏览器任务和批量 Agent 工作负载，尤其是需要管理执行时限、依赖和有限联网范围时。容器与轻量虚拟机的隔离和兼容性不同；多租户、出口策略及凭据处理也不是创建接口成功后自动具备，需要配置并验证。

当前生命周期服务默认采用单活部署，改用 PostgreSQL 不会自动获得通用多副本高可用；已支持的双副本协调范围也不能扩大解释。采用平台会减少应用重复实现环境管理的工作，同时增加控制面、网络、镜像和恢复链路的运维责任。
