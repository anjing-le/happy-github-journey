## 问题与目标

做门店周报时，“本周有效订单数”按下单时间还是支付时间统计，会得到不同结果。人可以找业务负责人问清楚，Agent 若只拿到一个名称和一段说明，就容易把某种口径直接当成答案。知识是否可靠，取决于定义是否明确、谁确认过、哪一版生效，以及查询时能否拿到相应版本。

本体平台把这些散落的业务约定组织起来，让人、业务系统和 Agent 共用一套可追溯的定义。它提供指标怎么算、关联哪些对象、有哪些限制；真正计算本周订单数仍交给业务系统，选择哪个口径也仍由业务负责人判断。

## 方案怎么做

先规定知识怎样表达。商户、门店、订单等业务对象，与指标维度、实际数据表分别建模，再用明确的关系连接。术语、事件、决策、分析方法和行动等知识解释业务怎样运转；约束负责限定哪些做法允许成立。例如“退款率持续偏高”是事件，“加入复核名单”是决策，二者不能混为一谈。图中的连接表示已有关系，不代表系统已经具备因果判断或逻辑推理能力。

再把“发现知识”和“让知识生效”分开。挖掘只产出候选，质量模块检查命名、归属和关系，管理模块负责确认、审批与发布。提交时同时检查已发布对象和在途草稿，避免同一个概念被重复建立。责任人确认绑定最终生效版本，稳定对象标识与可修改的名称分开，改名不会让原有关系失效。

审批也要能应对失败和并发：先保存本地审批记录，再启动外部流程；发布前比较修改起点、当前线上值与草稿值，两边改动冲突时交给人处理。状态以审批系统的权威结果为准，不能让前端猜测已经通过。回调丢失时定期对账并补偿，同一变更多次重试仍只发布一次。

通过治理的版本统一存入 MySQL，作为事实主记录。图库、全文索引和向量索引只承担查询，可以从主记录重建。这样换检索引擎不必重做整套治理；但“主记录已发布”和“检索侧已更新”是两个时刻，需要分别观察。

查询架构随需求逐步演进：最初按日建图，能查关系但更新慢、名称不一致时难命中；随后用 OpenSearch 搜索、GDB 查关系、Hologres 取明细，由应用按对象标识拼起来。再往后，MySQL 的变更经 CDC、Paimon 和 Flink 处理，将节点、关系和向量写入 NeuG，让关键词、向量和图查询使用同一套对象，减少跨库对齐身份与拼接结果的工作。

集中索引后，难点转到了同步链路。先导入已有对象，再持续消费变更；同批写入先节点后关系，重复投递不能产生重复对象，删除也要同步并清理关联。图与向量来自不同作业，文本更新后可能暂时没有新向量，不能据此承诺发布即一致。当前迁移也只是部分完成：管理台融合检索和按标识查明细已使用新链路，场景重算还在影子比对，OpenAPI、MCP、HSF 的主要检索与关系接口仍使用原有引擎。新旧双跑、比较对象集合与排序后再逐步切换，保留回退路由。

搜索时先让关键词和向量各自找候选，再从命中对象沿关系扩展，按各路名次融合，最后按需精排。关键词擅长准确名称，向量补充不同说法，图补充已知联系；精排只能调整已有候选，救不回前面漏掉的对象。精排失败时保留已有排序并说明降级；关系查询若因数量上限截断，也应说明没有查完，不能把空结果直接解释成没有知识。

为了让不同业务和 Agent 使用明确的范围，场景先圈定起点，沿关系展开，再保存一份子图快照并配发限定范围的凭证。快照让对象范围保持稳定，代价是底层修改后需重新计算。响应要带上快照时间，查不到时只说明本范围内未找到，不悄悄扩大到全库。圈选条件的并集、交集、遍历方向与数量上限都影响完整性；有很多节点不代表圈选正确或已经查全。

最后把知识按使用方式交付。页面、OpenAPI、HSF 和 MCP 共用核心定义、权限与审计，分别处理入口鉴权和返回形式。给 Agent 默认少量摘要，保留对象标识、版本、确认人与维护人，并说明哪些字段没取、怎样继续取，避免一次返回数百个字段挤满上下文。节省篇幅的同时，要让它仍能核对自己正在使用哪份知识。

## 适用条件与取舍

适合多个系统需要共享业务含义，而且口径会变化、责任需要明确的场景。业务必须愿意持续维护定义与归属，否则换再强的索引也无法补出缺失的知识。选架构应先看能容忍多长更新延迟、需要哪些查法、是否真的发生过跨引擎不一致，再判断是否值得增加流式链路和统一引擎的复杂度。

这套实现的写入口受到独占写租约约束，故障切换会有等待；查询和批量回填共享资源，也缺少在线只读副本，需要安排低峰任务并建设恢复能力。固定快照换来稳定范围，却增加更新等待；审批换来责任可追溯，却不证明定义绝对正确。

检索效果还要分层判断：有候选不等于候选有用，字面命中也不等于业务理解正确。应结合真实问法、同义改写和无答案问题检验，分别发现知识缺失、召回遗漏与排序问题。平台交付可核对的定义和边界，Agent 能否选对口径、解释正确并算出结果，还需要业务复核与独立验证。
