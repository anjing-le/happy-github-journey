## 问题与目标

导入文档、调用模型或处理多步订单，常常比一次 HTTP 请求持续得更久。进程重启会丢掉内存进度，重新运行又可能重复发消息、调用收费接口或修改外部状态。只有一个任务队列，还不足以说明每一步是否已经完成。

DBOS Transact 把应用中的流程、步骤和等待转成可持久记录的执行。开发者仍用 Python 组织业务逻辑，框架通过数据库保存输入、状态与步骤结果，让失败后的工作可以恢复，而不必从零编写一整套执行引擎。

## 方案怎么做

流程负责组织先后关系，步骤包住需要记录结果的具体工作。执行步骤前，框架按流程标识和步骤位置查找记录；已经完成的步骤可以复用结果，没有记录的步骤才真正运行，结果或错误随后写入存储。

因此恢复不是把进程内存原样搬回来，而是重新走流程代码，沿途复用已记录的结果。会变动的外部读取和有副作用的动作需要安排在合适的步骤里；流程代码升级也要考虑旧任务的执行顺序和版本兼容，不能随意改写后假定历史任务仍能正确重放。

任务调度同样依赖持久状态。多个执行器领取任务时，在数据库事务中协调候选记录、队列约束和归属，把真正领取到的任务改为执行中。恢复逻辑将需要恢复的任务重新排队，仍通过正常领取入口启动，避免恢复动作绕过并发和顺序限制。

例如一个文档处理流程可以先下载、再解析、最后通知。解析结果已经记录时，重启后可以复用；通知若没有可确认的结果，则还需要查明是否发送成功。这让流程进度与业务事实可以分别检查，而不是看到工作进程活着就认为整件事可靠。

关键缺口是外部动作与本地记录未必在同一事务。服务端已经接受付款，但步骤结果尚未落库就崩溃，恢复时仍可能再次调用。稳定业务幂等键、结果查询、对账或补偿必须与持久化执行配合，不能把可恢复流程理解为所有外部动作恰好发生一次。

## 适用条件与取舍

适合有长任务、等待、重试和后台队列，又希望保留普通代码开发方式的服务。数据库不仅保存业务数据，还承接调度与执行记录，因此容量、可用性、清理策略和任务版本都成为系统的一部分。

这套设计减少自建恢复机制的负担，也引入数据库访问与运行规则。可以借鉴其流程与步骤边界、统一领取与恢复入口，而不必因为需要一个简单异步任务就引入完整体系。代码采用 MIT 许可。
