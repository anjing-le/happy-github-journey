## 问题与目标

业务人员想知道一个数字，困难往往不只是不会写 SQL。即使会写，也可能选错表、漏掉过滤条件，或者把同名但不同口径的指标拿来比较。固定报表覆盖不了所有临时需求，直接查底表又依赖个人经验。

这套设计先把目标收窄到可靠取数与基础分析：让用户说清业务问题，拿到含义明确、来源可查、可以复核的结果。已有标准产品能满足时继续用标准产品；语义层与 Agent 重点承接尚未被覆盖的长尾需求，再逐步深入业务决策。

## 方案怎么做

核心是分开三种责任。语义层管理指标、维度、过滤条件和数据资产映射，回答“这个数字到底怎么算”；DSL2SQL 把结构化的业务请求转换成 SQL；云端 Agent 负责澄清问题、检索定义、组织查询和解释证据。例如查某类主播的收入，先确认对象、时间、收入口径和退款处理，再生成查询，而不是先猜 SQL、看到数字再解释。

数据建设、语义管理、业务分析分别由不同 Agent 承担，辅助 Agent 分担可拆解的工作，最终答复仍有明确负责人。多业务方共用聊天入口时，按身份路由到独立工作目录；业务定义按业务保留，个人沟通偏好跟随个人。目录隔离用来组织上下文，实际数据权限还需要独立校验。

语义资产也不能只靠填几个字段建出来。需求从报表或分析目标出发，沿血缘追到真实数据，核对字段、粒度和关联，再建立物理表、逻辑表、指标、维度与绑定关系。交付前检查关系、生成 SQL，并在相同日期和条件下与可信结果对账；资产创建成功只是其中一步。后续需求优先复用这些已验证的定义，上游变化也要沿依赖检查下游。

知识检索先限定范围，再寻找相关内容。Wiki-KBase 按业务域、页面和资产分层缩小候选，低相关时按模式扩大范围或补查术语与本体。不同模式的退路不同，不能一搜不到就无条件查全库。结果附带出处，无命中和低分记录进入问题清单，修复源知识后增量发布，再回放验证。检索分数和资产热度都是筛选信号，不是答案正确的证明。

取数走固定管道：语义核验、生成 DSL 与 SQL、执行、校验、交付。约束工具入口，防止临时手写 SQL 绕过语义；管道内部另检查依赖与过滤条件，后处理按真实表头读取，缺列直接报错，不能默认为零。执行失败、成功却零行、结果触及截断上限，都先当作未定状态核查，必要时在另一引擎按相同口径对账。交付同时保留查询、来源、条件、结果和执行凭据，使问题能定位到具体环节。

长会话不依靠模型记住所有规则。少量高频硬规则自动加载，台账和任务状态在行动前读取，大体量知识按需检索。反复出错或经业务确认的重要口径可以升到入口；稳定且能用程序验证的约束逐步固化到工具，再从提示词中移出。取数明细则按独立生命周期压缩和归档，分析产物尽量保留聚合结果与口径，避免重复复制全部明细。

数据供给先保证准确，再优化速度，为有明确时效要求的链路增加实时能力。Paimon 承担湖仓存储，StarRocks 等引擎提供查询服务；入湖仍要检查来源映射、分区、调度和消费权限。把表写进湖里，不会自动让整条链路实时，低延迟还涉及更新顺序、撤回和迟到数据等约定。

长期治理使用真实调用反馈。低风险检查可以自动执行，证据不足或风险高的事项转人工。资产下线要同时核对查询日志、依赖、年龄和保留规则；日志分页不完整时，“没查到使用”可能只是证据缺失。下线后继续观察使用回流，恢复另走审核流程。未知口径、异常数字和缺失资产先挂账，经确认后再补入语义层，使每次需求都能改善下一次取数。

## 适用条件与取舍

适合数据资产较多、口径需要统一、长尾分析需求频繁，而且能持续维护数据与语义的数据团队。代价不只是搭一个 Agent，还包括定义和审核口径、打通血缘与权限、维护查询转换器、校验器和治理责任。语义覆盖之外的问题要澄清或明确受阻，不能用临时 SQL 掩盖缺口。

可以借鉴的是分工、受约束的查询链路和反馈机制，不能照搬固定的检索阈值、资产评分权重或入口规则条数。双引擎一致也可能共享同一种错误口径，仍需要可信业务基准；校验器自身也要有合法与异常用例，避免误拦或长期失效。

当前已有取数、检索和治理的运行材料，但产品级稳定性测评、更广泛的语义覆盖及深入业务决策仍是持续建设目标。采用时应分别验证数值正确、异常处理、响应时效和完整用户流程，不能把调用量当作准确率。
